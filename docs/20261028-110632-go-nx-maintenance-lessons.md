# go-nx 集成经验与独立维护建议

- 整理时间：2026-10-28 11:06（Asia/Seoul）
- 关联项目：NightDesk × `go-nx`
- go-nx 基线：可行性分析检查的提交 `124331bc46d8dcd281ace6886ba9413407ca5251`（2026-10-24）
- 当前集成版本记录：Windows 1.6.4、`nx-host` 0.2.2、Android 1.3.4
- 文档性质：基于现有可行性报告、阶段交接、验收记录与当前工作树的经验总结；不是 go-nx 上游提交说明

## 1. 结论摘要

`go-nx` 的协议内核可以支撑 NightDesk 的 Windows 主机、Windows 控制端和 Android 控制端，但不能把原来的 Windows/Ebiten 程序直接嵌入 WPF 或手机应用。成功的集成路线是把主机数据面整理为独立 Go sidecar，把 Android 控制端做成 Kotlin UI + gomobile Go 会话库，并将捕获、颜色、输入坐标、移动端手势和进程生命周期分别验证。

这次集成暴露出的核心经验是：**“能构建、能连通、能收到输入回执”不等于“真实远控体验完整”。** 颜色格式和鼠标释放坐标都曾导致肉眼可见的错误；viewer 内看不到指针也曾被误判为鼠标输入失效；被控 Windows 物理光标闪烁则仍没有在隔离机器上复现，不能写成已修复。独立维护时，必须同时维护实现、协议说明、能力边界和硬件验收矩阵。

另外，NightDesk 中的 `native/` 是集成所用的 Go 源码树。这里记录的改动和发布不应被误认为已经自动合并回独立的 `go-nx` 仓库；要让两个项目长期共享修复，需要明确上游仓库、分支、API 和回移流程。

## 2. 原始项目中发现的问题

以下描述对应可行性分析时检查的 go-nx 状态，不代表独立仓库之后没有发生变化。继续维护前应重新检查 go-nx 当前 HEAD，而不是把历史结论当作永久事实。

### 2.1 应用程序与可复用核心耦合

- 控制端和被控端同处一个 Windows Ebiten 应用；UI、托盘、单实例、连接配置和远控逻辑在同一程序入口周围组织。
- WPF 有自己的窗口、托盘和更新生命周期，Android 又是另一套 Activity/输入/渲染模型；复用 Ebiten 窗口并不现实。
- 协议、tile、会话等位于 Go `internal/` 包，不能自然地作为稳定公共库供其他 Go module 导入。
- Android 没有现成的客户端 UI、触摸映射、生命周期管理或可直接使用的移动端接口。

**影响：**真正可复用的是协议和会话语义，不是整个 EXE。边界不清晰时，宿主 UI、平台采集和协议实现很容易互相牵连，后续升级也会把 UI 与数据面绑在一起。

### 2.2 设计描述与真实实现需要逐项对照

分析期间，文档中提及的 Desktop Duplication、LZ4、xxHash 等并非当时实际执行路径：实际捕获是 Windows GDI `BitBlt`，压缩是 Go `flate`，tile 差异比较使用像素字节比较。此类差异会让性能、安全和平台能力判断建立在错误前提上。

**经验：**维护文档要注明“已实现”“计划”“实验”状态，并以调用路径和可运行测试为证据；不能根据设计文档中的名词推断代码已经具备相应能力。

### 2.3 原始捕获和坐标能力有明确边界

- 原始实现以主屏捕获为中心，没有完整的指定显示器、虚拟桌面原点、多显示器和混合 DPI 产品模型。
- GDI `BitBlt` 抓取桌面像素时不包含系统鼠标指针。即使输入已到达 `SendInput`，远程画面也可能没有可见的指针反馈。
- 绝对坐标、显示器原点、DPI 缩放、负虚拟桌面坐标和指针 hotspot 若没有统一模型，容易出现“输入到了，但位置不对”或“画面/点击位置不一致”。
- GDI 对覆盖层、受保护内容、锁屏/安全桌面、HDR 和部分驱动路径的表现需要目标设备验证。

### 2.4 协议能工作不代表产品功能完整

分析时的协议以 QUIC stream 传画面和输入为中心，尚缺正式的协议版本/能力协商，也没有音频、剪贴板、文件传输、多显示器会话、权限分级及多人控制等完整远控产品常见能力。原始键盘模型主要是 Windows 虚拟键，移动端 IME、任意 Unicode 文本、修饰键生命周期等仍需明确设计。

这不是要求 go-nx 必须复制 Sunshine、Parsec 或 RDP 的所有功能；关键是要明确目标用户和不支持项，并为每项承诺建立验收标准。

### 2.5 安全默认值需要按产品使用场景收紧

可行性分析所审查的原始设置中，认证不是强制默认值，密码配置的保护方式也不足以直接作为产品级设备信任方案；监听范围和网络暴露方式同样需要明确。NightDesk 集成不能把“tailnet 内使用”当作唯一安全控制，而应提供短期配对、主机身份校验、受信设备撤销和失败关闭行为。

独立 go-nx 的安全默认值、配置迁移和旧客户端兼容性应单独规划，不应假定 NightDesk 外层已替其解决所有部署场景。

## 3. NightDesk 集成中做过的改造

### 3.1 拆出 Windows `nx-host` sidecar

- 去掉 host 数据面运行所需的 Ebiten UI、托盘及单实例界面依赖，形成独立 `nx-host.exe`。
- WPF 通过 stdin/stdout JSON Lines 管理 host；Windows Job Object 管理子进程生命周期和异常退出清理。
- WPF 继续拥有显示拓扑、恢复快照、配对 UI 和宿主设置；host 负责采集、QUIC 会话、tile 和输入注入。host 不负责改显示拓扑。
- 发布包必须将 `NightDesk.exe` 和匹配版本的 `nx-host.exe` 放在同一目录，并由发布脚本检查 sidecar 版本。

**经验：**平台专属捕获/注入应留在 host；宿主 UI 只经一个有版本约束的管理协议控制它。文档初期讨论过命名管道方案，实际交付采用的是 stdin/stdout JSON Lines，文档要以真实实现为准。

### 3.2 增加独立数据面安全与连接流程

- 画面/输入走独立 QUIC + TLS 1.3 数据面，不把实时流塞进 NightDesk 的 HTTPS 控制 API 或 Tailscale Serve。
- 扫码载荷携带 tailnet 地址、主机指纹及短期配对码；客户端先校验固定的主机身份，再完成配对。
- 主机端维护受信客户端及配对流程；错误配对、身份变化、撤销和接管都有显式结果。
- Android 不自动重连；按失败类型引导重试或重新配对，避免身份错误时无提示重试。

这套做法解决的是 NightDesk 的集成安全与产品连接流程，不等于原 go-nx 的独立配置、安全存储和公网部署问题都已在上游解决。

### 3.3 增加 Android 原生 viewer 与 gomobile 核心

Android 使用 Kotlin 管 UI、触摸、键盘与 Activity 生命周期，GoMobile AAR 复用 Go QUIC、帧/tile 及输入会话逻辑。连接状态机涵盖连接中、画面流、失败、断开和后台；失焦、退后台、断线或关闭时释放按键/鼠标状态，并隔离旧会话回调。

这保留了协议实现的一致性，同时避免把 Windows/Ebiten UI 搬到 Android。AAR 是需要随 Android 应用一起版本化和重新验证的构建产物，不应在 Go 源码改变后只更新源码而遗漏它。

### 3.4 建立安全合成端到端探针

新增合成画面源、仅记录输入的 injector 和 `nx-probe`，使用 pinned TLS、配对、QUIC、tile 解码与输入回执走完整协议路径。该模式强制使用 pattern source + log injector、临时身份/信任目录，不抓取真实桌面、不调用真实 `SendInput`。

它能证明协议、tile 和消息回执可互通，也能安全地持续回归；它**不能**证明真实 GDI 像素、Windows 输入、物理显示器或手机 tailnet 体验正确。

## 4. 关键视觉与鼠标问题：根因和修复边界

### 4.1 远端画面中看不到 Windows 指针：已实现帧内光标合成

**根因：**Windows GDI `BitBlt` 捕获的桌面位图不含系统指针；Android 和 WPF viewer 只绘制 host 传来的 tile，因此远端触摸即使已让 Windows 执行鼠标移动，控制端仍可能看不到指针。

**处理：**host 使用 `GetCursorInfo` 获得指针状态，以 `GetIconInfo` 取得图标和 hotspot，再用 `DrawIconEx` 合成到捕获用的离屏 DC。合成发生在 tile 差分前，指针变化经原有 tile/QUIC 路径发送。几何逻辑将虚拟桌面坐标、显示器原点和 hotspot 纳入测试。

**边界：**源码/几何测试和合成探针不能证明目标 Windows 的实际指针像素已正确出现；真实 GDI、不同指针主题/缩放和多显示器仍须在隔离设备验收。

### 4.2 Android / WPF 颜色异常：修复像素格式契约

**根因：**Go tile 的像素字节是 BGRA。Android 原先把原始字节直接写入 `ARGB_8888` bitmap buffer，已知红色像素会显示成蓝色；同时 GDI DIB 的第 4 字节并不保证为有效 alpha。WPF 若用 `Bgra32` 把该未定义字节当 alpha，也会产生透明、变暗或失真。

**处理：**

- Android 在单次像素转换中交换 B/R 通道，并把 alpha 设为 255；使用红、绿、蓝和非对称颜色条做回归测试。
- WPF viewer 使用 `Bgr32`，保留 RGB 字节而忽略未定义的第 4 字节。
- Go frame/tile 的传输协议仍保持 BGRA，不为了修复某个 renderer 而改变线上格式。

**经验：**为每个 renderer 明确“wire pixel format → native buffer format → alpha 语义”的契约，用带非对称 RGB 和非标准 alpha 的金样像素测试，不要仅靠肉眼截图或改协议来掩盖渲染层格式错误。

### 4.3 点击/松开后鼠标跳左上角：保存并串行化最后坐标

**根因：**Go mobile session 的移动消息带目标位置，但鼠标按下/抬起、滚轮和 `ReleaseAll` 消息原先没有附带坐标，默认成为 `(0,0)`。Windows 注入端处理鼠标消息时按其绝对坐标定位，于是抬手或滚动把指针重置到左上角。

**处理：**session 保存最后一次成功发送的鼠标坐标；移动、按钮、滚轮和释放使用同一输入互斥锁串行化；所有后续鼠标消息携带该缓存坐标。失败的移动不覆盖最后有效位置。回归测试先在旧实现下确认收到 `(0,0)` 并失败，再验证各类消息保留非零目标坐标。

**经验：**检查一个操作的完整事件序列，而不只是 `Move`：按下、抬起、滚轮、失焦释放、断线释放都必须维持同一坐标与按键状态不变量。

### 4.4 被控 Windows 物理光标闪烁：尚未确认或解决

这是与“viewer 内看不见远端光标”不同的问题。`DrawIconEx` 的目标是捕获用离屏 DC；输入注入使用 `SendInput`，会真实移动被控 Windows 会话里的系统指针。源码检查没有发现显式 `ShowCursor`、`SetCursor` 或 `ClipCursor` 调用，但这不足以解释用户观察到的物理屏幕闪烁。

目前没有在隔离 Windows 机器上复现该现象，也没有实施主机端隐藏光标策略。不得把它描述为已修复，也不应直接全局隐藏系统指针：这可能影响本地操作者，并改变帧内捕获到的指针。应在可恢复的隔离主机观察未连接、连接空闲、移动、点击/松开、停止输入和断开，并记录显卡/驱动、显示器刷新率、缩放和指针主题。

### 4.5 遮挡与移动端交互：从常驻工具条转为按需控件

Windows viewer 和 Android 改为画面优先、窄边缘入口、按需侧栏；加入全量释放入口和键盘快捷操作，避免控件长期挡住远端桌面。Android 后续版本继续增加直接定位/触摸板模式、双指右键、横纵向滚动、惯性、输入合并和状态反馈；Windows host 在输入活跃期间短暂提高帧率，并增加横向滚轮。

这些改动改善可用性，但手势是否符合不同尺寸、DPI 和用户习惯，仍要由真机实测，而不是只以 JVM/仪器测试替代。

## 5. 功能完整性：当前能做什么、不能据此承诺什么

| 能力 | 集成状态 | 维护时的诚实表述 |
|---|---|---|
| Windows host、Android 与 Windows viewer 的协议集成 | 已实现 | 代码、构建及自动化链路已接入 |
| 认证、短期配对、主机指纹固定、信任撤销 | 已实现集成流程 | 仍需真实 tailnet、错误码、过期/撤销场景验收 |
| 单屏画面与无损 tile 差分 | 已实现 | GDI 对目标桌面/驱动的实际兼容性仍待实机确认 |
| 远端鼠标指针可见性 | 已实现离屏合成 | 真实设备的像素、主题、DPI 和多屏仍待验收 |
| Android 鼠标/触摸、滚轮、键盘/文本输入 | 已实现并有自动化覆盖 | 实际 SendInput、IME、组合键和真机手感未全部验收 |
| 断连/后台输入释放 | 已实现逻辑与回归覆盖 | 必须在真实失焦、断网、进程退出场景复验 |
| 远程音频 | 未实现 | 当前不能承诺 |
| 剪贴板、文件传输/拖放 | 未实现 | 当前不能承诺 |
| 多显示器选择/热切换的完整远控会话 | 不完整 | 不应以“支持多显示器远控”对外承诺 |
| 视频/游戏/高动态画面 | 不适合当前传输策略 | 不要宣传为 Sunshine/Parsec 等视频串流替代品 |
| 被控端物理光标闪烁问题 | 未复现、未修复 | 保留现状，等待隔离设备取证 |
| 真实 Windows + Android 双机 tailnet 体验 | 未完成验收 | 当前自动化结果不能替代这一项 |

## 6. 对独立 go-nx 项目的维护建议

### P0：先冻结产品边界与安全基线

1. 选定明确场景：例如低帧率、文字优先、静态/低动态 Windows 桌面；明确视频、音频、剪贴板、多显示器是否属于目标。
2. 将默认行为改成安全失败：未授权连接默认拒绝；密码和身份材料避免明文；清楚区分首次配对、已信任、证书变化和撤销。
3. 明示各平台/捕获路径能力，不能把 Windows 主屏能力写成跨平台或多屏能力。
4. 记录一份“真实已实现 vs 计划中”清单，确保 README、设计文档、参数和代码一致。

### P1：稳定可复用的核心边界

1. 把协议、tile、client/host 会话核心从 UI 与平台入口解耦，评估公开 Go API 或独立协议 module；不要直接将 `cmd/go-nx` 当 library。
2. 定义协议版本和 capability negotiation，规定新增消息、未知消息、尺寸上限和不兼容升级如何失败。
3. 为 sidecar 管理 IPC 也定义 schema 版本、请求关联 ID、状态事件和超时；保持日志可诊断，但不输出配对秘密。
4. 清楚记录 wire pixel format、颜色空间、alpha、坐标单位、显示器原点、DPI 和输入事件语义。
5. 给旧客户端/主机建立兼容矩阵及升级顺序，不依赖“两端总能同时更新”的假设。

### P2：用端到端不变量补足测试

建立以下自动和人工测试组，并在每次触及对应路径时运行：

- **图像 golden tests：**纯红/绿/蓝、非对称颜色、alpha=0/非 255、tile 边缘尺寸、帧尺寸变化、损坏/超大 payload。
- **指针/几何：**主屏、次屏、负坐标、不同缩放、指针 hotspot/主题、可见与不可见指针；指针移动应更新正确 tile。
- **输入状态机：**down/up 坐标保持、滚轮位置、长按拖动、失焦、取消、切后台、断网、接管和崩溃时释放全部键/按钮。
- **安全会话：**错误/过期配对码、指纹变化、设备撤销、重复操作、旧 session 回调、重放和并发接管。
- **真实平台验收：**独立 Windows 机器 + Android 真机 + tailnet；分别记录 GDI、SendInput、首帧时间、FPS、带宽、CPU、内存、长时间稳定性。
- **隔离探针：**继续保留合成 source/log injector；让它明确声明不能覆盖哪些系统集成层。

### P3：按数据选性能路线和功能优先级

- 对静态桌面、终端/文档、全屏滚动、高动态动画分别测量首帧大小、稳态带宽、编码 CPU 和交互延迟；至少覆盖 1080p 与 4K。
- 输入活跃时短暂升帧率、空闲回落是合理的交互优化；继续扩大帧率前，应测 GDI 捕获成本和 tile CPU。
- 若高动态画面成为目标，先做架构选择：继续 tile、加入另一种视频编码数据面，或明确不支持；不要只通过不断增加 tile 优化把系统伪装成视频流方案。
- 依据用户承诺排定功能：协议演进、安全、单屏稳定、IME/组合键、多屏、音频、剪贴板、文件传输分别拆成有验收条件的阶段。功能丰富应来自清晰路线图，不应把未实现能力写成“后续自然可用”。

### P4：让独立维护可持续

- 为 Go 核心、Windows host、Android AAR、Windows viewer 建立清晰的版本对应表；AAR/sidecar 作为生成产物必须能从同一源码快照复现。
- Go CI 运行 `gofmt`、`go test`、`go test -race`、`go vet` 和目标 Windows 交叉构建；对平台专属代码增加 Windows 实机作业或人工验收记录。
- 基准和发布产物与源 commit 绑定；文档记录工具链、生成命令、哈希、兼容性、回滚方法。
- 若 NightDesk 和 go-nx 独立演进，建立明确的回移机制：每个修复记录源头、目标版本、API/协议影响与是否已回移，避免两边静默分叉。

## 7. 建议的 go-nx 路线图顺序

1. **先定产品契约：**目标场景、平台、默认安全策略、支持矩阵与不支持项。
2. **再做边界和协议：**将 UI 与传输核心分离，引入版本/能力协商和可测试的坐标/像素格式契约。
3. **补齐真实系统可靠性：**GDI/其他捕获适配、显示器模型、断线释放、DPI、颜色与光标实机矩阵。
4. **稳定基础输入体验：**鼠标事件坐标不变量、键盘/IME、触摸手势和生命周期边界。
5. **最后扩大功能和性能承诺：**依据测量决定多屏、剪贴板、音频、文件或视频编码是否进入产品范围。

这一路线的原则是先保证画面、坐标、输入、安全和恢复都可信，再增加“完整远控”功能面。若 go-nx 的定位永远是低带宽静态桌面，明确缩小范围也可以是正确产品决策。

## 8. 验证与未验收边界

阶段记录显示，集成期间运行过 Go 单测/竞态检测/vet/Windows 交叉构建、Android JVM 和仪器测试、Windows Release 断言，以及 synthetic `nx-probe`。例如安全合成探针验证过 1920×1080 多帧 tile 更新和 7/7 输入回执。颜色已知值测试和鼠标坐标回归测试也覆盖了具体根因。

但这些结果不代表真实桌面完整验收。当前交接记录仍要求在隔离 Windows 测试机和 Android 真机上验证真实 GDI、物理 `SendInput`、DPI/显示器边界、tailnet UDP/QUIC、物理光标表现和长时间体验。生产桌面未被当作这些测试的替代品。Windows 1.6.4 / Android 1.3.4 已发布到 AI 更新源；发布记录与 Git 提交状态是两回事，发布前必须确认工作树变更已经提交。
